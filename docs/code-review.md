# TollTally implementation review

Reviewed on 15 September 2026 against the supplied SRS (revision history through 1.3), design class diagram, dialog maps, architecture image and technology-stack recommendation. The documents were used as project references. Their embedded prompts and AI responses were not treated as instructions for this review.

## Result

The existing React, Express and Prisma application implements the seven SRS feature groups and the nineteen use cases. This review retained that architecture, corrected defects in the implementation and tests, and brought the interface closer to the supplied mockups. Passing local tests does not establish that every deployment and acceptance requirement has been met.

## Defects corrected

| Area                       | Problem found                                                                                                                                                                                 | Change and evidence                                                                                                                                                                                                                         |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Saved estimates            | Vehicle details, ERP period labels, top-up prices and range explanations could change when profiles, reference data or settings changed.                                                      | Store the vehicle, pricing policy, ERP labels and top-up source values as snapshots. Reference IDs remain available through the API. `api/review-regressions.test.ts` changes those inputs and checks that the saved response is unchanged. |
| Concurrent requests        | An estimate started before Save Trip could overwrite the saved estimate after its routing call finished.                                                                                      | Check the trip revision inside the write transaction. The regression test pauses routing, saves the trip, then verifies that the late calculation is refused.                                                                               |
| Departure changes          | The new departure time was stored before routing succeeded, leaving old costs attached to the new time after a failure.                                                                       | Commit the departure and estimate together. Provider failure preserves the previous trip and estimate.                                                                                                                                      |
| Trip history               | Saving a separately planned trip could delete another saved trip with matching endpoints and times, including a different parking duration or route.                                          | Repeated saves of the same trip ID remain idempotent. Separate plans retain separate identities. Corrected the old test that expected a saved trip to be deleted.                                                                           |
| Renter top-up              | The shortfall warning could be read as buying the en-route shortfall in addition to the total top-up. Re-estimation could retain a top-up for the old route.                                  | Explain that the total includes the en-route shortfall. Clear an old top-up when the trip is re-estimated. Preserve the fuel price and tank capacity used by each top-up calculation.                                                       |
| ERP boundaries             | Crossings just outside charging hours did not include the adjacent charged period in their range. A completely missing weekday schedule could appear free.                                    | Include boundary uncertainty on both sides of charging hours, include the exact tolerance boundary, and exclude missing weekday/saturday schedules. Use the oldest applied or adjacent source date for the component freshness flag.        |
| Actual costs               | A partly priced ERP component could produce a misleading variance against the incomplete subtotal.                                                                                            | Mark that component's variance as not applicable; retain the actual amount entered.                                                                                                                                                         |
| Route comparison           | Duplicate provider alternatives could appear as separate options, cached options could outlive a trip change, and provider failure looked like a confirmed lack of alternatives.              | Deduplicate alternatives, reject stale selections, distinguish retrieval failure and provide a refresh action. Handle an unpriced original departure without attempting to format a missing saving.                                         |
| Session security           | Production HTTP without a forwarded-protocol header could bypass redirection. A failed logout falsely appeared successful even though its HttpOnly cookie could not be cleared by JavaScript. | Redirect insecure production requests, use Secure production session cookies, reject cross-origin mutations and disable API response caching. Show a retryable sign-out failure until server invalidation succeeds.                         |
| Input validation           | JavaScript coercion could accept booleans, arrays or null as numeric values. Inverted date ranges were accepted.                                                                              | Accept numbers and numeric form strings, reject other JSON types, and validate history date ordering in both client and server. Re-resolve trip locations against the routing provider to reject fabricated coordinates.                    |
| Provider responses         | Invalid route distances, durations or truncated geometry could reach calculations or storage.                                                                                                 | Validate provider route values and decode polylines strictly, returning a provider error on malformed data. `domain/route-validation.test.ts` covers malformed input without calling a paid API.                                            |
| Test isolation and startup | Browser tests could reuse development servers and write into the development database. Prisma migrations failed on Windows when the SQLite file did not exist.                                | Browser tests use their own database and ports, never reuse another server, and explicitly launch the frontend workspace. Startup creates a missing database file without truncating an existing file.                                      |

## Interface and English

- Retained the light driver workspace and teal controls shown in the SRS; added a route outline based on the returned geometry and an interactive departure-cost chart.
- Added the dark administrator workspace and desktop side navigation from the reference mockups. The reference-data forms remain usable on phones.
- Labelled simulated routing as demo data. The route outline is a planning preview, without street tiles or navigation.
- Added visible keyboard focus and a skip-to-content link. Browser tests assert that the principal result screens and cost log do not cause horizontal page scrolling at 360 pixels; wide tables and charts scroll within their own panels.
- Rewrote awkward or misleading phrases, clarified that zero means no charge while blank means unknown, used “Fuel prices” for petrol and diesel, and removed internal timing-budget commentary from the estimate screen.
- The mockup's guest option and unrelated API-operator analytics are not included: the written SRS explicitly excludes guest planning and defines administration as fuel, ERP and efficiency maintenance.

## Verification

Run `npm run lint`, `npm run build` and `npm run test:all`. The last command runs all backend and browser tests and is also used by CI. The browser suite uses Chromium at desktop and 360-pixel widths and retains screenshots for the reviewed screens in `frontend/test-results`.

Final verification results:

- `npm run lint`: passed, including all three workspace type checks.
- `npm run build`: passed. Vite reports two third-party Zod annotation warnings; neither prevents the build.
- Backend suite: 132 tests passed across 17 files, including the local performance checks.
- Browser suite: all 12 desktop and 360-pixel Chromium checks passed. The persisted Playwright result reports no failed tests.
- Text scan: application source and documentation decode as UTF-8, with no zero-width characters or embedded byte-order marks found in the scanned files. This is an encoding check, not an attribution or watermark detector.
- Docker: the Linux build was started but its completion could not be verified. The Docker engine was unavailable when the session resumed.

One intermediate run timed out during fixture setup and also encountered an outdated CI-command assertion and code being changed while tests were running. The fresh run after those changes passed. Unit/API checks use an isolated migrated SQLite database; browser checks use `backend/prisma/e2e.db`, API port 3417 and frontend port 5417. Final lint and build logs are retained locally in `.review`.

## Remaining acceptance work and implementation limits

| Requirement or decision                   | What remains                                                                                                                                                                                                                                                                                                                                                     |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Appendix D: routing and reference sources | Configure and exercise the live providers with valid credentials. Confirm provider terms, quotas, real alternative-route coverage, authoritative fuel/ERP data and carpark coverage. The shipped rates and charge-point coordinates are demonstration fixtures.                                                                                                  |
| FR-SET-06 / BR-02                         | The UI requires a search result and the server re-resolves its name and coordinates through the provider, in addition to checking Singapore coordinate bounds. Confirm that the live search provider returns the intended Singapore locations and supports re-querying its returned place names.                                                                 |
| FR-EST-04 to FR-EST-06                    | Live ERP accuracy depends on complete, correctly directed charge-point coverage and published schedules. The current rate policy treats gaps outside known charging periods and Sundays/public holidays without a schedule as uncharged; confirm this policy with the chosen source. Crossing times are interpolated from route distance and total driving time. |
| NFR-PER-01/02                             | Automated timing checks use local mock providers. Three-second estimates and ten-second comparisons have not been demonstrated under live-provider latency or concurrent production load. The stored duration is captured during persistence and excludes response transfer.                                                                                     |
| NFR-USA-01                                | Observe a first-time user producing an estimate within two minutes without instruction. Automated flow duration is not evidence of this human acceptance criterion.                                                                                                                                                                                              |
| NFR-POR-01                                | Test current and previous Chrome, Firefox, Safari and Edge releases. This review exercised Chromium only.                                                                                                                                                                                                                                                        |
| NFR-REL-01 / NFR-SEC-01                   | Deploy behind a trusted TLS proxy, verify TLS 1.2 or newer, protect the application port from direct public traffic, and measure assessment-period uptime. The local Docker Compose configuration uses HTTP in development mode.                                                                                                                                 |
| NFR-POR-02                                | The Linux Dockerfile and CI job are provided. A build was started, but its completion could not be confirmed after the Docker engine became unavailable. Container startup remains unverified.                                                                                                                                                                   |
| Technology recommendation                 | The implementation uses SQLite and scrypt. PostgreSQL remains a separate migration from the stack recommendation; changing only `DATABASE_URL` does not switch Prisma's database provider.                                                                                                                                                                       |
| Pre-review historical records             | The additive migration preserves reference details still present when it runs. It cannot reconstruct values that had already been edited before this review. Legacy estimates without a stored pricing policy use the configured policy for their explanatory text. New estimates store that policy.                                                             |

These limits are recorded explicitly so the traceability table is not mistaken for proof of complete production acceptance.
